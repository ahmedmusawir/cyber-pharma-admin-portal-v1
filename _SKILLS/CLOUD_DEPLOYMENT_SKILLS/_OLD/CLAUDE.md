# CLOUD DEPLOYMENT SKILLS — Next.js → Cloud Run

This folder contains a **2-skill deployment package** for deploying Next.js applications to Google Cloud Run. These skills are designed to work together in sequence.

## What's Here

```
CLOUD_DEPLOYMENT_SKILLS/
├── CLAUDE.md                          ← You are here
├── next-deploy-generate/
│   ├── SKILL.md                       ← Skill 1: File generator
│   └── references/
│       └── TEMPLATES.md               ← Canonical file templates
└── next-deploy-execute/
    └── SKILL.md                       ← Skill 2: Deployment walkthrough
```

## The Two Skills

### Skill 1: `next-deploy-generate`

**Purpose:** Ask the user a series of questions about their app, then generate a complete deployment package — `Dockerfile`, `cloudbuild.yaml`, `deploy.sh`, `init-app.sh`, and `DEPLOYMENT_CHECKLIST.md`.

**Triggers:** "next deploy", "generate deployment files", "suit up for deployment", "give me the cloud files", "prep for cloud run", "deployment package", or any request for Cloud Run deployment artifacts.

**How it works:** Read `next-deploy-generate/SKILL.md` for the question flow and generation rules. Read `next-deploy-generate/references/TEMPLATES.md` for the canonical file templates. Do NOT generate files from memory — always use the templates.

### Skill 2: `next-deploy-execute`

**Purpose:** Walk the user step by step through running the deployment files, setting up DNS/SSL, and verifying everything works.

**Triggers:** "deploy now", "run the deployment", "let's ship it", "walk me through deploying", "push to cloud run", or any request to actually execute a deployment (not generate files).

**How it works:** Read `next-deploy-execute/SKILL.md` for the guided walkthrough phases. This skill assumes the deployment files already exist. If they don't, redirect the user to Skill 1 first.

## Order of Operations

1. **Generate first** → Skill 1 produces the deployment files
2. **Execute second** → Skill 2 walks through running them

Never skip Skill 1. The deployment files must exist before Skill 2 can guide the user.

## Where Generated Files Go

All files generated by Skill 1 go in the **project root** (next to `package.json`), NOT inside this `CLOUD_DEPLOYMENT_SKILLS/` folder:

```
your-app/
├── CLOUD_DEPLOYMENT_SKILLS/    ← Skills live here (don't touch)
├── Dockerfile                  ← Generated by Skill 1
├── cloudbuild.yaml             ← Generated by Skill 1
├── deploy.sh                   ← Generated by Skill 1
├── init-app.sh                 ← Generated by Skill 1
├── DEPLOYMENT_CHECKLIST.md     ← Generated by Skill 1
├── src/
├── package.json
└── ...
```

## Key Concepts (Quick Reference)

### 3-Layer Secret Mapping

Your code reads generic env var names (`process.env.STRIPE_SECRET_KEY`). Locally, `.env.local` provides values. In GCP, Secret Manager stores values under app-prefixed names (e.g., `starkreads-stripe-secret-key`). The `--set-secrets` flag maps them at deploy time. Your code never changes between apps.

### Build-Time vs Runtime Secrets

Build-time secrets are needed during `next build` (SSG/ISR pages). They go in `availableSecrets` + `secretEnv` + `--build-arg` in `cloudbuild.yaml` and `ARG`/`ENV` in the Dockerfile. Runtime secrets are needed when the container runs. They go in `--set-secrets` in the deploy step only. Some secrets are both.

### Public Vars vs Secrets

`NEXT_PUBLIC_*` vars are public — they get embedded in client-side JavaScript. They go in `deploy.sh` as plaintext substitutions, NOT in Secret Manager. Everything else is a secret.

### Naming Conventions

- Secret Manager: `{app-name}-{secret-name}` (e.g., `starkreads-stripe-secret-key`)
- Service Account: `sa-{app-name}-runtime` (e.g., `sa-starkreads-runtime`)
- Cloud Run Service: `{app-name}-prod` (e.g., `starkreads-prod`)
- Domain: `{app-name}.cyberizedev.com` (e.g., `starkreads.cyberizedev.com`)
